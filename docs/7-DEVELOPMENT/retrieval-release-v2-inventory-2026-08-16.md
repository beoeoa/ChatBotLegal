# Retrieval Release V2 — inventory, chunking and acceptance contract

The V2 release treats PostgreSQL's 12,236-document inventory as the source
snapshot. The 7,245-document baseline and 3,000-document candidate remain
immutable historical experiment inputs.

The read-only audit is:

```powershell
python scripts/audit_retrieval_source_inventory_v2.py
```

Each document receives exactly one provisional state:

- `current_retrievable`: observed in serving scope and effective at the audit date;
- `historical_only`: observed as expired/repealed/replaced or otherwise historical;
- `quarantined`: missing source/identity/content/scope or unresolved effectivity.

The audit intentionally does not treat database status as official legal review.
Every row remains review-required until the official source, validity interval,
jurisdiction and reviewer attestation are recorded in the additive release
workflow.

V2 chunking is additive. V1 chunks and vectors are never rewritten. The
canonical splitter first isolates Điều/Phụ lục and Khoản/Điểm boundaries, then
uses the pinned tokenizer to create windows of at most 512 tokens with 64-token
overlap only inside the same structural child. Empty, duplicate, unassessed or
out-of-scope chunks are not eligible for embedding.

Serving routes `temporal_scope=historical` to the collection named by
`LEGAL_CHROMA_TEMPORAL_COLLECTION`; current queries use the active current
collection. If that variable is absent, the runtime retains the M2 active
collection as a compatibility fallback, but the V2 release gate does not treat
that fallback as proof of a separate temporal index.

The evaluation contract is `retrieval-eval-suite-v1`: Golden regression 1,000,
Hard-negative 500 and sealed Production holdout 500, balanced across five
domains with current, historical, temporal refusal, insufficient-facts,
out-of-scope, exact identity, procedure, multi-issue and validity-trap quotas.
The validator fails closed when the suite is incomplete; existing 100-case
files are not silently promoted.

The current legacy-input audit confirms Golden-1,000 has 1,050 expected-source
rows but no official URL, jurisdiction or validity interval fields, while the
Hard-negative-100 has 196 source rows with the same missing review fields. These
inputs remain development evidence and are not promoted to the v1 acceptance
suite.

An additional read-only review queue maps 1,454 legacy source references to the
12,236-document inventory where possible: 1,369 have one observed inventory
match and 85 remain unmatched. It deliberately leaves `official_url`,
jurisdiction, validity and reviewer approval empty until legal QA attests them.
The queue is at
`reports/retrieval-release-v2/retrieval-eval-review-queue-v1.json` and is not a
benchmark suite.

The complete 12,236-document metadata proposal queue is generated by
`scripts/build_retrieval_metadata_review_queue_v2.py`. Each proposal now keeps
the observed pre-review values in `observed_values`, so a reviewer can submit
an exact before/after correction. Applying such a correction is handled only
by `scripts/apply_retrieval_metadata_attestation_v2.py`: it requires the queue
and inventory file hashes, an official-host evidence URL/checksum, a real
reviewer identity and a self-hashed attestation. Its output is a staging
overlay plus an audit report; it never writes PostgreSQL, the source snapshot,
Chroma or the active pointer. The contract is
`retrieval-metadata-attestation-v1.schema.json`.

The eventual three-way suite assembly is implemented by
`scripts/assemble_retrieval_eval_suite_v1.py`. It refuses legacy inputs,
requires exact 1,000/500/500 split counts, shared dataset/source/manifest
fingerprints, a sealed holdout and a matching holdout checksum sidecar. No
combined suite is written until those checks pass.

Final production-answer acceptance is separately audited by
`scripts/audit_retrieval_release_v2_acceptance.py`; it requires passing M5/M6,
full-answer p95/correctness/citation/fallback evidence and Golden-294
regression evidence. Missing evidence produces a BLOCKED artifact rather than
being inferred from retrieval metrics.

No active pointer, baseline collection, live metadata or real vector collection
is changed by the audit/validation commands.

The inventory gate now validates positive, numerically unique document IDs,
the exact three-state partition, the canonical SHA-256 of the 12,236-document
source snapshot and its detached file checksum. The official-web observation
packet is accepted by the aggregate gate only as `EVIDENCE_ONLY`; it must keep
`approved_for_import=false`, retain legal-review-required status and prove that
the database, vector collections and active pointer were not mutated. The
packet therefore documents the 46-reference source gap without silently
promoting any source into the release.

The corresponding release-quality artifact is
`quality-policy-v2-release-passage-v3.json`. Its `quality_gate_passed` is true
for the V2 draft; `legal_release_approved` and `release_gate_passed` remain

older `quality-policy-v2-assessment-tokenized.json` remains a separate legacy

## Staging release chain

After legal attestation is supplied, the release chain is intentionally
ordered as follows:

```powershell
python scripts/approve_retrieval_chunk_manifest_v2.py `
  --manifest reports/retrieval-release-v2/legal-retrieval-chunk-manifest-v2-draft-passage-v3.json `
  --attestation reports/retrieval-release-v2/legal-review-attestation-v2.json `
  --output reports/retrieval-release-v2/legal-retrieval-chunk-manifest-v2-approved-passage-v3.json

python scripts/build_retrieval_release_v2_shadow.py `
  --manifest reports/retrieval-release-v2/legal-retrieval-chunk-manifest-v2-approved-passage-v3.json `
  --target legal-retrieval-v2-current-shadow `
  --document-state current_retrievable `
  --output reports/retrieval-release-v2/legal-retrieval-v2-current-shadow.report.json `
  --apply

python scripts/build_retrieval_release_v2_shadow.py `
  --manifest reports/retrieval-release-v2/legal-retrieval-chunk-manifest-v2-approved-passage-v3.json `
  --target legal-retrieval-v2-temporal-shadow `
  --document-state all `
  --output reports/retrieval-release-v2/legal-retrieval-v2-temporal-shadow.report.json `
  --apply

python scripts/build_retrieval_release_v2_lexical_index.py `
  --manifest reports/retrieval-release-v2/legal-retrieval-chunk-manifest-v2-approved-passage-v3.json

python scripts/build_retrieval_serving_manifest_v3.py
```

The last command emits the checksum-bound `legal-serving-manifest-v3` staging
pointer only when current/temporal vector reports and SQLite exact/FTS5 bind to
the same release, source snapshot and chunk manifest. The benchmark runner
requires that pointer and verifies it again at runtime; none of these commands
activates the production pointer.

The V2 runtime now materializes an allowlist from eligible, retrievable chunk
revision IDs in the approved chunk manifest. Exact lookup, lexical lookup,
vector hydration and parent/neighbor expansion all reject IDs outside that
allowlist; SQL scope predicates also bind the release ID and effective interval
for the requested temporal scope. A runtime without that allowlist fails closed
instead of treating an index or collection response as sufficient authority.
Startup also verifies the chunk identity checksum and the release-pointer
content checksum before opening the serving path.

Fresh V2 Chroma metadata also records `document_serving_state` and normalized
effectivity bounds. The ANN branch now applies the current-versus-temporal
state filter before hydration; SQL hydration remains the second fail-closed
check for the exact `legal_as_of` interval. The V3 pointer builder includes
`quality_policy_version` in the provenance tuple required by the schema, so a
pointer cannot bind a vector release whose quality policy is ambiguous.

Before M5, run
`python scripts/audit_retrieval_eval_source_availability_v2.py`. This checks
every answer-required positive source against the approved V2 chunk manifest,
including law/article identity and current versus historical serving state.
The release gate consumes this report and blocks any source-availability rate
below 100%; metadata-only or legacy Golden mappings cannot count as retrieval
evidence.

`api.retrieval_serving_manifest_v3.load_v3_serving_manifest()` is now the
single loader for the V3 release pointer. It validates the atomic checksum,
the 12,236-document state partition, duplicate document IDs, retrievable versus
quarantined chunk counts, collection/index fingerprints and (when requested)
the exact-index file checksum. The legacy
`api.legal_serving_scope.load_serving_manifest_scope()` explicitly rejects a
V3 pointer with `v3_release_pointer_requires_v2_runtime`; this prevents the V1
integer chunk-ID server from consuming a V2 string revision-ID pointer.

This boundary is intentional until the V2 runtime is wired into the public
serving path under a separate approved activation slice. A V3 pointer being
present on disk is not evidence that production is serving V3.

### Release pointer contract clarification

`legal-serving-manifest-v3.json` is the atomic Retrieval Release V2
**release pointer** and carries `kind=release_pointer`. It binds the current
and temporal Chroma collections, the exact/lexical index, the approved chunk
manifest and the provenance tuple. The older
`legal-serving-manifest-v3.schema.json` contract remains the per-collection
manifest from the earlier Feature 018 slice; it is not a substitute for the
release pointer and cannot be used to activate a V2 release.

The legacy evaluation inputs were also passed through the V1 validator in
read-only mode. The validator now emits a bounded console summary on
Windows, while retaining the full error list in
`reports/retrieval-release-v2/golden-legacy-validation.json` and
`reports/retrieval-release-v2/hard-negative-legacy-validation.json`. Both
remain FAIL and are not promoted: the Golden input is a Feature 016 schema,
and the Hard-negative input contains only 100 cases in a different schema.

## Write-path safety

All release builders reject a target that aliases
`active_core_collection.txt` through the shared
`api.retrieval_release_contracts.require_staging_collection_target()` guard.
This covers the V2 shadow builder, candidate/unified legacy builders, quality
rebuild, filtered scope rebuild and benchmark reordering. The legacy
`/import` path in `scripts/legal_search_server.py` is also fail-closed by
default: it raises `direct_active_collection_mutation_disabled` before any
database or vector write. `LEGAL_ALLOW_LEGACY_DIRECT_IMPORT=1` is reserved for
isolated compatibility tests or an explicitly approved rollback operation and
is not set by the live configuration. New corpus work must therefore use a
versioned staging chunk release/index job and keep the M2 pointer unchanged.

The actual baseline Chroma write barrier was independently verified in
`reports/retrieval-release-v2/baseline-write-lock-verification.json`: all 20
collection-scoped triggers are present, the baseline write probe is blocked,
the active pointer still names the baseline, and a non-baseline probe remains
rollback-safe. The release gate consumes this evidence rather than assuming a
lock from source code alone.

M6 also records the learned-reranker runtime mode, scored count, degraded
fallback count and device for every evaluated case. A benchmark cannot pass
by silently falling back to heuristic ranking or CPU inference: the learned
gate requires mode `learned`, zero degraded/OOM cases and CUDA execution.

## Fail-closed blocker artifacts

The V2 shadow-vector and exact/lexical builders now persist a checksum-bound
`status=BLOCKED` report when invoked with the provisional draft manifest. The
reports explicitly record the rejection reason and prove that no collection,
SQL index, baseline or active pointer was mutated:

- `v2-shadow-build-blocked-20260816.json`
- `v2-lexical-index-blocked-20260816.sqlite3.report.json`

The three-way evaluation assembler likewise writes an
`*.assembly-blocked.json` report when the sealed Production holdout or any
shared fingerprint is missing. It never writes a partial 2,000-case suite.
These are audit evidence for a blocked release, not substitutes for legal
attestation, a reviewed Hard-negative-500 or the sealed Holdout-500.

Pointer cutover is rehearsed by
`scripts/rehearse_retrieval_release_v2_pointer.py` in a temporary sandbox. It
verifies candidate switch and rollback while comparing the real pointer before
and after; a missing or invalid V3 candidate produces a BLOCKED report and no
live pointer write.

The aggregate V2 gate also compares the live pointer value with the expected
M2 baseline collection, not merely with itself before and after the check.

An evidence-only official-source review packet now covers all 19 law numbers
represented by the 46 unresolved references. It distinguishes local absence
from source non-existence and records observed effectivity, including
historical-only findings for 15/2021/NĐ-CP and 62/2021/NĐ-CP. The packet keeps
`approved_for_import=false`; it is not a substitute for a legal reviewer,
full-text checksum and metadata attestation.

The M5/M6 runner also persists a `status=BLOCKED` report on preflight failure
(missing approval, suite, source-availability report, collection or
fingerprint), so an attempted benchmark cannot be mistaken for a failed or
partial acceptance run.

The runner validates the complete 2,000-case suite but deliberately evaluates
only `golden-regression` and `hard-negative` when selecting an M5/M6
configuration. The sealed `production-holdout` cases are recorded as pending
and cannot influence experiment ranking; they require a separate frozen
acceptance run after the candidate configuration is fixed.

That independent run is
`scripts/run_retrieval_release_v2_holdout_acceptance.py`. It accepts only a
passing M5/M6 report and its selected experiment, refuses configuration
overrides, requires `holdout_sealed=true` and exactly 500 cases, then reports
the holdout metrics and safety/latency gates without changing live state.

The winner selection is now safety-first: M5 orders safety, candidate
Recall@50, Recall@10, MRR, multi-source coverage and latency; M6 orders safety
with learned CUDA execution, Recall@10, MRR, multi-issue coverage and
latency. M5 additionally requires exact law/article lookup and final
Recall@10 to be 100% on tagged cases. M6 requires correct refusal at least
99% and multi-issue required-source coverage at least 95%; answer citation
support remains a separate full-answer acceptance gate.

M5's control explicitly enables exact law/article lookup and disables issue
splitting. The vector Top-K, lexical Top-K and RRF/weighted-fusion members
carry those same values; the only exception is the deliberately named
`m5-exact-lookup-disabled` and `m5-issue-splitting` ablation. The weighted
family uses `m5-fusion-weighted-060-040` as its anchor, then changes only the
vector/lexical weights. M6 copies the retrieval knobs from the selected M5
experiment, so rerank Top-N and expansion are measured without silently
switching the retrieval parent. The runtime trace now records a separate
`candidate_union` stage (exact + vector + lexical, before scoring fusion) and
its latency/Recall@50, so candidate absence is not conflated with a later
fusion-rank loss.

### Local reranker artifact manifests

The V2 M6 runner now verifies a release-scoped local-only manifest before it
loads either learned reranker. The BGE and GTE manifests include model-file
size/SHA-256, pinned revision and the fixed M6 contract (`max_length=512`,
batch size 8, Top-N 20/30/50/100). GTE additionally includes the pinned
`Alibaba-NLP/new-impl` custom-code snapshot and verifies `configuration.py`
and `modeling.py`; it cannot resolve remote `auto_map` code at runtime. These
artifacts are benchmark-only and do not alter the BGE snapshot, live
configuration or active pointer. Generate or refresh them with
`scripts/prepare_retrieval_release_v2_reranker_manifests.py`, then pass the
corresponding manifest to the V2 M6 command.

### Provisional V2 embedding and serving staging

The draft chunk manifest may be used only for an explicitly named
`*provisional` Chroma collection, SQLite index, or serving pointer. The
staging builders require the draft's review blocker, record
`provisional_staging=true` and `release_eligible=false`, and keep the M2
active pointer unchanged. The V2 passage encoder uses `max_length=512` with
the pinned VNLegal-LAL recipe; pending chunks are processed in deterministic
token-length order to reduce padding without changing IDs or checksums. A
provisional V3 pointer is rejected by the runtime and aggregate release gates
unless an isolated staging caller explicitly opts in. It is therefore useful
for integrity and filter smoke tests, but it cannot be promoted as legal
evidence or used to claim a production gate.

Vector verification reuses the same fixed 512-token passage contract as the
builder for both CUDA replay and CPU/GPU parity. A replay performed with the
legacy 2,048-token default is not valid evidence for this release.
